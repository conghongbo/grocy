## Priority and dependencies

P0 establishes the common foundation. P1 proves it through system reads and a complete Tasks workflow. P2 covers smaller modules and shared files; Chores may start with fixture-backed product selectors, but stock-consuming chores cannot pass acceptance until the stock dependency is verified. P3 establishes master data and stock behavior. P4–P6 build on those contracts; P7 closes administration and full parity.

Design bootstrap, calendar/report read adapters, user-selector access and extension compatibility in P0, even where the screen lands later. Otherwise late discovery of inaccessible data can invalidate a standalone-SPA design. Permission and settings support starts in P0; it is not postponed until the final administration screens.

## Procedure for each adapter and page

1. Select the actual route/controller/service and corresponding Blade/view script from the catalogue. Record permission, complete request DTO, success media type/shape, failure paths, related entities and UI-only behavior. Apply the correction register first.
2. Capture a legacy workflow against disposable, identified fixtures with known flags, settings, timezone and role. Store request/response metadata and resulting records/logs with secrets removed. If capture is not yet possible, retain an explicit “source expectation, unverified” label.
3. Implement an endpoint adapter using the common transport. Map wire types to UI state at that boundary; serialize an explicit write DTO. Use generic CRUD only where the entity/method is exposed.
4. Build the page workflow, including selectors, validation/defaults, cancel, empty/error state, permissions, settings, accessibility and legacy navigation parameters. Reuse React components rather than attaching legacy jQuery to React-owned DOM.
5. After a mutation, use returned IDs/transaction rows for follow-up work and refresh affected data. Preserve drafts on failure and distinguish confirmed success with failed follow-up from an unconfirmed network result. Do not automatically repeat a business mutation.
6. Run the relevant scenarios below and the earlier per-route matrix; retain receipts and compare persisted effects. A screenshot, status 200, successful build or OpenAPI-generated type alone does not establish functional parity.
7. Enable that page through the chosen coexistence mechanism. Record rollback and data dependencies; update route coverage when backend source changes.
